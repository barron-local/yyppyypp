1. หมวดเครือข่าย Cisco Switch L3 & Router (เกณฑ์ข้อ 3.5.1: 13 คะแนน)

13 คะแนนเต็ม
[สรุปเกณฑ์คะแนนส่วนที่ 1]

- 1.1 VLAN server, dev, guest (ห้ามใช้ VLAN 1): 1 คะแนน (วงละ 0.33)
- 1.2 Inter-VLAN Routing (มี IP ทั้ง 3 วง และ Route ถึงกันได้): 3 คะแนน (ไม่ครบได้ 0)
- 1.3 DHCP Server เครื่องเดียวแจก 3 วง + DHCP Snooping เฉพาะ Port ที่กำหนด: 3 คะแนน
- 1.4 NAT ทุก VLAN เพื่อออกเครือข่ายกรรมการ: 1 คะแนน
- 1.5 ACL ควบคุมการสื่อสาร (Standard, Extended, กั้น Server, Management) + Loop Protection: 5 คะแนน

[ขั้นตอนที่ 1.3] การตั้งค่า DHCP Server 3 เครือข่าย และ DHCP Snooping ▶

ตั้งค่า DHCP Pool ให้แจก IP ทั้ง 3 วง และเปิด DHCP Snooping ให้เชื่อถือเฉพาะ Port ขา Uplink:

! กัน IP ไม่ให้แจกทับ Gateway และ Server
ip dhcp excluded-address 192.168.10.1 192.168.10.50
ip dhcp excluded-address 192.168.20.1 192.168.20.20
ip dhcp excluded-address 192.168.30.1 192.168.30.20

! Pool สำหรับ Server
ip dhcp pool POOL_SERVER
 network 192.168.10.0 255.255.255.0
 default-router 192.168.10.1
 dns-server 192.168.10.10
exit

! Pool สำหรับ Dev
ip dhcp pool POOL_DEV
 network 192.168.20.0 255.255.255.0
 default-router 192.168.20.1
 dns-server 192.168.10.10
exit

! Pool สำหรับ Guest
ip dhcp pool POOL_GUEST
 network 192.168.30.0 255.255.255.0
 default-router 192.168.30.1
 dns-server 192.168.10.10
exit

! ตั้งค่า DHCP Snooping
ip dhcp snooping
ip dhcp snooping vlan 10,20,30
no ip dhcp snooping information option

! กำหนด Port Fa0/1 เป็น Trusted Port (ยอมรับ DHCP Server เฉพาะ Port นี้)
interface FastEthernet 0/1
 ip dhcp snooping trust
exit

! Port ลูกข่ายกำหนด Rate Limit ป้องกันการยิง DHCP DoS
interface range FastEthernet 0/2 - 24
 ip dhcp snooping limit rate 15
exit
[ขั้นตอนที่ 1.4 - 1.5] การตั้งค่า NAT, ACLs และ Loop Protection ▶ 
! 1. ป้องกัน Loop บน Switch (STP BPDU Guard)
spanning-tree mode rapid-pvst
spanning-tree portfast default
spanning-tree portfast bpduguard default

! 2. Standard ACL: จำกัดสิทธิ์เข้า Management VLAN
access-list 10 permit 192.168.20.0 0.0.0.255
access-list 10 deny any

line vty 0 4
 transport input ssh
 access-class 10 in
exit

! 3. Extended ACL: กั้น Guest เข้า Server ยกเว้น Web (80, 443) และ DNS (53)
ip access-list extended ACL_PROTECT_SERVER
 permit tcp 192.168.30.0 0.0.0.255 192.168.10.0 0.0.0.255 eq 80
 permit tcp 192.168.30.0 0.0.0.255 192.168.10.0 0.0.0.255 eq 443
 permit udp 192.168.30.0 0.0.0.255 host 192.168.10.10 eq 53
 deny ip 192.168.30.0 0.0.0.255 192.168.10.0 0.0.0.255
 permit ip 192.168.30.0 0.0.0.255 any
exit

interface vlan 30
 ip access-group ACL_PROTECT_SERVER in
exit

! 4. NAT Overload บน Router ออกไปหาเครือข่ายกรรมการ
access-list 1 permit 192.168.10.0 0.0.0.255
access-list 1 permit 192.168.20.0 0.0.0.255
access-list 1 permit 192.168.30.0 0.0.0.255
ip nat inside source list 1 interface GigabitEthernet 0/1 overload

2. หมวดเซิร์ฟเวอร์และระบบ DevOps Infrastructure (เกณฑ์ข้อ 3.5.2: 24 คะแนน)

24 คะแนนเต็ม
[จุดตัดคะแนนสำคัญที่ต้องระวัง]

- DNS Server: ต้องรันบน Docker หรือ Linux Server เท่านั้น หากตั้งค่าบน Router, Switch หรือไฟล์ hosts จะไม่ได้คะแนน (0 คะแนน)
- Sudo NOPASSWD: ต้องกำหนดให้ user สามารถพิมพ์ `sudo -i` โดยไม่ต้องใส่รหัสผ่าน (1 คะแนน)
- CI/CD Pipeline: ต้องมี 4 Stages (build, test, push, deploy) ทำงานสำเร็จทั้งหมด หากได้แค่อย่างใดอย่างหนึ่ง จะไม่ได้คะแนน ไม่มีการหารเฉลี่ย (2 คะแนนเต็มหรือ 0 ทันที)

[ขั้นตอนที่ 2.1 - 2.3] ตั้งค่า Ubuntu Server, Users, Sudo NOPASSWD และ UFW ▶

รันสคริปต์นี้บน Ubuntu Server VM (`192.168.10.10`):

# 1. ตั้ง Hostname
sudo hostnamectl set-hostname server.competition.lab

# 2. เพิ่ม 2 Users และให้สิทธิ์ sudo
sudo useradd -m -s /bin/bash devops_admin
sudo useradd -m -s /bin/bash app_deployer
echo "devops_admin:Password123!" | sudo chpasswd
echo "app_deployer:Password123!" | sudo chpasswd
sudo usermod -aG sudo devops_admin
sudo usermod -aG sudo app_deployer

# 3. ตั้งค่า Sudo NOPASSWD (-i)
echo "devops_admin ALL=(ALL) NOPASSWD: ALL" | sudo tee /etc/sudoers.d/99-devops
echo "app_deployer ALL=(ALL) NOPASSWD: ALL" | sudo tee -a /etc/sudoers.d/99-devops
sudo chmod 0440 /etc/sudoers.d/99-devops

# 4. ตั้งค่า UFW Firewall เปิดเฉพาะพอร์ตที่กำหนด
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp    # SSH
sudo ufw allow 80/tcp    # HTTP
sudo ufw allow 443/tcp   # HTTPS SSL
sudo ufw allow 53        # DNS
sudo ufw allow 5000/tcp  # Registry
sudo ufw allow 8080/tcp  # GitLab
sudo ufw --force enable
[ขั้นตอนที่ 2.2] รัน Technitium DNS บน Docker พร้อมตั้ง ACL IP Restriction ▶ 
# คำสั่งรัน Technitium DNS Container
docker run -d \
  --name technitium-dns \
  --restart always \
  -p 53:53/udp \
  -p 53:53/tcp \
  -p 5380:5380/tcp \
  -e DNS_SERVER_ADMIN_PASSWORD=AdminPassword123! \
  -v technitium_data:/etc/dns \
  technitium/dns-server:latest

วิธีตั้งค่าใน Web GUI (http://192.168.10.10:5380):
1. เมนู Zones -> Add Zone ชนิด Primary Zone ชื่อ `competition.lab`
2. เพิ่ม A Records ชี้ไปที่ `192.168.10.10` ได้แก่ `gitlab`, `registry`, `app`, `api`
3. เมนู Settings -> Allowed Networks / Access Control -> เลือก Restricted ใส่เฉพาะ `192.168.10.0/24, 192.168.20.0/24` เพื่อผ่านเกณฑ์ ACL IP Restriction

3. การออกแบบระบบ ผังงาน และ API Specification (เกณฑ์ข้อ 4.1 - 4.4: 20 คะแนน)

20 คะแนนเต็ม
[เกณฑ์ 4.1] ผังงาน 5 รูปแบบที่ต้องส่ง (5 คะแนน) ▶

ดูแผนผัง Mermaid ฉบับสมบูรณ์ได้ที่ไฟล์ 01_System_Design/FLOWCHARTS_AND_DIAGRAMS.md:

  1. Login Flow: รับ Username/Password -> ตรวจสอบข้อมูล -> Hash Check (bcrypt) -> สร้าง JWT Token -> แยก Role นำทาง
  2. Admin Process: จัดการผู้ใช้งาน (เพิ่ม/แก้ไข/ลบ/กำหนด Role) -> จัดการ Categories -> ตรวจสอบ Logs
  3. User Level 1 Process (Officer): แสดงตารางข้อมูล -> ค้นหา/กรอง -> เพิ่มรายการ + แนบไฟล์ -> แก้ไขข้อมูล/ไฟล์
  4. User Level 2 Process (Member): คลังข้อมูลสำหรับสืบค้น (Read-Only) -> ค้นหา -> ดูรายละเอียด -> ดาวน์โหลดไฟล์แนบ
  5. Use Case Diagram: แสดงความสัมพันธ์ระหว่าง Actor (Admin, Officer, Member) กับ 10 Use Cases ในระบบ
[เกณฑ์ 4.2] โครงสร้างฐานข้อมูลเชิงสัมพันธ์ 3 ตาราง (5 คะแนน) ▶

ตารางทั้ง 3 ต้องมี Foreign Keys เชื่อมโยงกันอย่างถูกต้อง (Relational Design):

1. users: id (PK), username (UQ), password_hash, full_name, email (UQ), role ('admin','user1','user2'), created_at
2. categories: id (PK), code (UQ), name, description, created_at
3. items: id (PK), category_id (FK → categories.id), created_by (FK → users.id), item_code (UQ), title, value_amount, status, attachment_name, attachment_path, created_at, updated_at
[เกณฑ์ 4.3] ผังหน้าจอ 5 หน้าใน Draw.io (5 คะแนน) ▶

วาดใน Draw.io แบบ Offline ให้ครบทั้ง 5 รูปแบบ (ดูไกด์ที่ WIREFRAMES_DRAWIO_GUIDE.md):

  • Template 1: หน้าจอเข้าสู่ระบบ (Login Screen) มีกล่องการ์ดกึ่งกลางและแจ้งเตือนสิทธิ์
  • Template 2: หน้าจอหลักของระบบ (Overview Dashboard) มี 4 KPI Stat Cards, กราฟ และกิจกรรมล่าสุด
  • Template 3: หน้าจอผู้ดูแลระบบ (Admin) มีตาราง User Management, ปุ่มเพิ่มผู้ใช้, Modal แก้ไขสิทธิ์ และ Modal ยืนยันการลบ
  • Template 4: หน้าจอผู้ใช้งานระดับ 1 (Officer) มี Search, Category Filter, ตาราง CRUD, ปุ่มเพิ่มข้อมูลพร้อมแนบไฟล์
  • Template 5: หน้าจอผู้ใช้งานระดับ 2 (Member) แสดงแบบ Read-Only Grid Cards สำหรับค้นหาและดาวน์โหลดเอกสาร (ไม่มีปุ่มลบ/แก้ไข)
[เกณฑ์ 4.4] การออกแบบ RESTful API Specification (README.md) (5 คะแนน) ▶

ตรวจสอบไฟล์ README_API_SPECIFICATION.md ซึ่งระบุคุณสมบัติต่อไปนี้ครบถ้วน:

  • ใช้ HTTP Methods ตามมาตรฐานสากล: GET (ดึง), POST (สร้าง), PUT/PATCH (แก้ไข), DELETE (ลบ)
  • ตั้งชื่อ Endpoint สื่อความหมาย เช่น `/api/items`, `/api/items/:id`, `/api/auth/login`
  • โครงสร้าง JSON สม่ำเสมอ `{ status, message, data }`
  • ระบุ HTTP Status Codes: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 500 Server Error
  • มีคำอธิบายระบบรักษาความปลอดภัยด้วย Bearer JWT Token

[1] GET พร้อมรับค่า: รองรับ Query (`?search=...&page=1`) และ Path (`/api/items/:id`)

[3] Upload File API: ใช้ Multer จัดการจัดเก็บไฟล์ลงโฟลเดอร์ uploads
[4] JWT Login: Signing ด้วย Secret Key และตรวจสอบสิทธิ์ผ่าน Header Bearer
[5] Exception Handling: ดักจับ 404, ข้อมูลไม่ครบ, Error ด้วย Error Middleware
[6] Response JSON มาตรฐาน: ส่งรูปแบบ `{ status, message, data }`
[7] มี Comment อธิบาย: เขียน JSDoc Comments อธิบายครบทุก Method (GET, POST, PUT, DELETE)
[8] ระบุข้อมูล Query, Path, Body: ชี้แจงไว้ในโค้ดชัดเจน
[9] โครงสร้างอ่านง่าย: แยก Router, Controller, Middleware, async/await
[10] ความปลอดภัยของ API: Role Middleware ป้องกันการเข้าถึงข้อมูลข้ามสิทธิ์

6. การนำเสนอผลงานและเฉลยแนวคำถามกรรมการ 3 ข้อ (เกณฑ์ส่วนที่ 5: 10 คะแนน)

10 คะแนนเต็ม
[คำถามข้อที่ 1: ด้าน Backend & Security] (3 คะแนน)
"ทำไมถึงเลือกใช้ JWT ในการยืนยันตัวตน และถ้าผู้ใช้ทำการ Logout หรือต้องการระงับสิทธิ์ทันที จะทำให้ Token ใช้งานไม่ได้อย่างไร?"
แนวทางการตอบ:
"เราเลือกใช้ JWT เพราะเป็น Stateless Authentication เหมาะกับ Web App ยุคใหม่ ไม่ต้องเก็บ Session ลง RAM ใน Server ทำให้รองรับโหลดได้สูงและมีความปลอดภัยด้วย Digital Signature (HMAC-SHA256)
กรณีต้องการ Revoke หรือตัดสิทธิ์ Token ทันที สามารถทำได้ 2 วิธี:
1. Token Blacklist ใน Redis: เก็บ Token ที่ถูกยกเลิกไว้ใน Redis พร้อมตั้งค่า TTL ตามเวลาหมดอายุเดิมของ Token เมื่อมี Request เข้ามา ให้ Middleware เช็ค Blacklist ก่อน
2. Token Versioning: เพิ่มฟิลด์ `token_version` ในตาราง Users และใน Payload ของ Token เมื่อต้องการตัดสิทธิ์ ให้บวกเลข version ในตารางเพิ่มขึ้น เมื่อ Token เก่าส่งมา version จะไม่ตรง และถูกปฏิเสธทันทีครับ"
[คำถามข้อที่ 2: ด้าน Frontend & UX/UI] (3 คะแนน)
"ระบบของคุณมีการจัดการ Error Handling ระหว่าง Frontend กับ Backend อย่างไร เพื่อไม่ให้หน้าเว็บค้าง หรือทำให้ผู้ใช้งานสับสน?"
แนวทางการตอบ:
"เราใช้สถาปัตยกรรมแบบสองชั้น (Two-tier Error Handling):
1. ฝั่ง Frontend (Client Validation): มีการดักจับข้อมูลเบื้องต้นก่อนส่ง (เช่น ช่องที่จำเป็นต้องกรอก, มูลค่าต้องไม่ติดลบ) ทำให้ผู้ใช้ทราบทันทีโดยไม่ต้องรอ Round-trip ไปยัง Server
2. การสื่อสาร JSON มาตรฐาน: ฝั่ง Backend ดักจับ Exception ด้วย Error Middleware และส่ง HTTP Status Code ที่ตรงตามมาตรฐาน (400, 401, 403, 404, 500) พร้อม JSON รูปแบบ `{ status, message, data }`
3. Frontend Error Translation: ฝั่ง Frontend นำ error message หรือ code มาแปลงเป็นข้อความภาษาไทยที่เข้าใจง่าย (Friendly Message) ผ่าน Toast Notification และ Error Box ใต้ฟอร์ม โดยไม่มีการปล่อยให้หน้าจอค้าง หรือแสดง Error ดิบทางเทคนิคครับ"
[คำถามข้อที่ 3: ด้าน DevOps, Network & Troubleshooting] (3 คะแนน)
"ถ้าในขั้นตอน CI/CD Pipeline ขั้นตอนที่ 4 (Deploy) เกิดข้อผิดพลาด Failed ขึ้นมา คุณมีกระบวนการตรวจสอบและ Rollback อย่างไร และทำไมจึงต้องแยก VLAN และมี Reverse Proxy?"
แนวทางการตอบ:
"กระบวนการตรวจสอบและกู้คืน (Rollback):
1. เข้าไปดูที่ GitLab CI/CD Job Logs เพื่อหาสาเหตุ เช่น ปัญหา Port Conflict, Database Migration ไม่ผ่าน หรือ Container Healthcheck Fail
2. ใช้คำสั่ง `docker logs` บนเซิร์ฟเวอร์เพื่อดู runtime log เชิงลึก
3. หากเป็นปัญหาของโค้ดใหม่ ให้ใช้ฟังก์ชัน Rollback ของ GitLab เพื่อ Redeploy Docker Image Tag เวอร์ชั่นก่อนหน้าจาก Private Registry ทันที ซึ่งใช้เวลาเพียงไม่กี่วินาที
เหตุผลที่ต้องแยก VLAN และใช้ Reverse Proxy:
- การแยก VLAN (Server, Dev, Guest): เพื่อจำกัด Broadcast Domain และเพิ่มความปลอดภัย โดยใช้ ACL กั้นไม่ให้เครื่องภายนอกเข้าถึงวง Server ได้โดยตรง
- Reverse Proxy (NPM/Caddy): ทำหน้าที่เป็น Single Entry Point สำหรับจัดการ SSL/HTTPS รวมศูนย์, ซ่อนพอร์ตจริงของคอนเทนเนอร์ภายใน, ป้องกันการโจมตีโดยตรง และช่วยทำ Load Balancing ครับ"
